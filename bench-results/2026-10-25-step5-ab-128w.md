# Step-5 A/B: 128 single-record writers, pre-Step-4 vs HEAD

Apple M2 (8 cores), 8 GB RAM, macOS Darwin 25.1.0 arm64, rustc 1.92.0, release
profile. One stream, unique keys, 200 single-record appends per writer, 128
writers, fresh temp dir per run, background compaction disabled,
`max_index_ram_mb=1024`.

- PRE  = `429900a` (before the narrowed write lock / batch changes)
- HEAD = `0ed92f9`

Both builds shared one `target/`; runs alternated PRE, HEAD, PRE, HEAD, ... Five
runs per config per mode. The value marked `*` is the preliminary run before the
alternating sequence and is excluded from the median.

## Observations

- Flusher rate was 112–118 fsync/s in every run except HEAD embedded run 2
  (72 fsync/s), which produced 9,185 ops/s — exactly 72 × 128, i.e. one full
  128-record batch per fsync. That run is a host disk stall, not a code
  regression; avg batch was 128.00 in all runs.
- Removing `write_lock` from the per-record ack wait did not change throughput
  at 128 writers, because the flusher already coalesces the whole writer cohort
  into one batch. The gain is latency for low-concurrency writers and the
  removal of a writer-starvation path, not peak ops/s.
- Per-run p99 was not captured for every A/B run. Absolute write latency on this
  host is fsync-bound and noisy; see `2026-10-25-step4-128w.md` for the p50/p99
  distribution (p99 12.7–54.0 ms across runs).
